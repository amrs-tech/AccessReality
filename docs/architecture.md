# Architecture and operating policy

One Next.js16 / React19 / TypeScript6 application, Node22, deployable on Vercel. Native server fetch handles SerpApi, `@google/genai` handles schema-constrained Gemini, and `@supabase/supabase-js` accesses Postgres exclusively on the server. No provider calls occur during rendering, exporting or building.

## Private boundary

`GET /api/session` returns a short-lived HttpOnly bootstrap cookie and its signed CSRF token. Access-code exchange requires exact Origin and that token. Successful sessions receive a cryptographically random opaque HttpOnly SameSite=Lax cookie, Secure on HTTPS. Only SHA-256 session hashes enter the database; expiration/revocation are authoritative. Failed-code attempts use a privacy-preserving HMAC network identity and an atomic5/15-minute bucket.

All mutations require Origin plus session-bound CSRF (admin uses an owner bearer secret plus Origin). Every private route checks job→session ownership, including export, cancel and reassess. Creates validate candidate ownership through the completed discovery job. Request bodies are streamed with a16KB limit and strict Zod schemas. No browser Supabase client or provider secret. Internal tables have RLS, no public/anon/authenticated grants/policies, and service-role-only invoker RPCs. Service-role bypass means application ownership checks remain mandatory.

## Transaction boundary

The browser sends sequential versioned step requests. A SQL transaction locks the owned job, checks version/session/terminal state, and acquires a75-second lease. The step route declares Node runtime and static `maxDuration=60`; provider deadlines are at most25 seconds inside a45-second application window, with time reserved for persistence. Each step contains at most one billable search or model request. A stale balance is checked using the free Account API before the lease is claimed. Expanded runs permit at most 128 workflow steps and five active minutes; older runs preserve their saved limits. Closed/hidden/offline pages start no further steps.

Before dispatch, `reserve_provider_attempt` locks job → cache → lexically sorted budget buckets. It rechecks the cache under lock, checks kill switches and every cap, then inserts an auditable reservation and increments counters atomically. `mark_dispatch` commits before network I/O and rechecks the kill switch. Completed or uncertain action keys cannot dispatch again. Known transient failures can reserve one separate later retry; all such attempts count toward caps. No serial SDK retry (Gemini SDK attempts explicitly1).

`commit_step` uses lease/version compare-and-swap to atomically save immutable sources/claims, corpus links, report revisions, cache response, attempt completion and workflow state. Late commits cannot overwrite newer state. Source IDs are canonicalized to the exact venue/group/text/retrieval snapshot on cache reuse. Canonical venue IDs derive from observed provider identity, never a name. Changed text has a separate immutable snapshot.

Expired leases inspect their attempts: provably undispatched reservations can be released with audit, but dispatched/uncommitted work becomes uncertain/consumed and cannot replay. Expired cache leases can be reconciled in a separate transaction locking the original owner job first. A second job waits; it never stampedes an identical cold-cache request. Cancel conservatively preserves spent/uncertain work and invalidates late commits. Recovered terminal jobs derive a conservative, fixed-time partial projection from their saved corpus if no finalized revision exists.

## Evidence and assessment

Maps labels use a versioned exact English mapping and JSON pointer. Negative attributes are processed first; absent attributes create no claim. Reviews/snippets are bounded, public-only immutable text, with review IDs and source-group hashes, actual source links and publication/edit/retrieval dates. Source text masks explicit unnecessary personal details while preserving UTF-16 offsets. Search snippets never claim a full page was reviewed. Ambiguous brand/branch matches remain in the ledger but are excluded before model extraction and cannot affect fit.

The verified Gemini wire schema retains required fields, enums and object structure while omitting decoder string/array bounds; full local Zod validation enforces every bound after the response. Scope and condition strings must be copied verbatim. The extraction version is `gemini-public-evidence-v3-verbatim-scope`. A successful SerpApi review response with absent reviews is empty only when its observed `reviews_results_state` is exactly `No reviews`; unexplained missing arrays remain schema failures.

The verified Google organic empty shape is HTTP200 plus `Success`, `Fully empty`, the exact documented no-results message, and absent or empty `organic_results`. Only that combination produces zero web sources; arbitrary provider errors and malformed arrays remain failures. Migration006 timestamps trusted balance receipt with the database clock and validates the observation's elapsed time against its database-issued snapshot, so clock differences between hosts cannot fabricate freshness.

Supplementary image references come only from [Maps listing thumbnails](https://serpapi.com/maps-place-results) and [review photos](https://serpapi.com/google-maps-reviews-api) in the existing provider responses. Listing references live in `Venue.images`; attached review references live in `Source.images` and are persisted in existing immutable JSONB snapshots/revisions. Each retains the exact provider search ID, JSON pointer, original source link and retrieval time; capture time remains null. No SQL migration or image storage service is needed. Reviewer avatars, profile URLs, credential-bearing URLs and provider proxy links are excluded. Browser-safe validation restricts direct HTTPS images to the six known Google photo CDN hosts and observed photo paths; CSP permits only those hosts.

The corpus retains at most24 photo references and the gallery displays12 distinct images, lazily and without a referrer. Checkpoint pressure removes optional image references before text/claims. Images do not enter Gemini, action choice, assessment eligibility or freshness. A photo-only review requires an observed review ID and has an empty excerpt; both outstanding-source selection and immutable extraction batching exclude empty text. The image format changes cache hashes only for Maps/details/reviews, preserving web snippet caches. Earlier saved reports remain unchanged and explain when no photo references were retained.

Migration 004 separates Gemini's owner-configured 1000-attempt ceiling from provider account quota. That provider balance remains unknown (`null`); initialization preserves used counters, never presents a made-up provider balance, and increases need an explicit audited owner allocation.

Gemini receives only public branch context/excerpts, never visitor priorities, diagnoses or private requirements. JSON schema permits source ID, known feature/polarity, exact quote and bounded scope. The server controls all provenance. Validation checks corpus/venue, exact span, feature entailment, questions, negatives, conditions, instructions and speculative claims. Unvalidated multilingual semantics stay unclear. Rejected proposals are recorded as bounded validation reasons and prevent favorable partial fit. A small synthetic evaluation set is not evidence of live model reliability.

Assessment is a pure function of corpus, requirements and an explicit UTC `asOf`. It is separate from extraction and never uses the model to declare fit. Scope-specific support cannot satisfy an unspecified entrance/floor. Conditions stay unresolved. Undated attributes remain insufficient; retrieval does not date a venue observation. Structural freshness180 days, operational14 days are product heuristics, not standards. Edit date never refreshes an original observation. Lift presence cannot imply operation, and even recent operation asks for confirmation before arrival.

Comparable support and barriers remain conflicting. Recent must-have barrier → reported barrier; unresolved/conflicting/historical must-have or relevant extraction failure → needs confirmation; only supported must-haves with complete required evidence processing → evidence supports requirements. Preferred support cannot hide a must-have barrier. Questions are deterministic and never sent automatically.

## Visit Watch: a separate, explicit news check

`POST /api/jobs/[id]/news-check` accepts only an idempotency key. The server and migration007 authenticate an unexpired private session and its saved completed/partial investigation, recover the canonical venue and city from the owned completed discovery, and snapshot the saved brief's generation time. A client cannot supply another venue, query, engine, allocation or budget. `GET` returns only the latest owned stored check and performs no provider call. Creation replay also performs no balance, rate-limit or reservation work.

The service-only `create_news_check` RPC adds an auxiliary `news_check` job with no private requirements, zero Gemini allowance, two search attempts and four steps. It shares the existing lease, version, cache, reservation, dispatch fencing, ambiguity and cancellation functions. Preflight007 verifies19 private invoker RPCs. The step endpoint rechecks both parent and child ownership. Known transient failures permit one later separately reserved retry; uncertain dispatch remains consumed and terminal. The news runner commits no accessibility sources, claims or assessment revision and never changes the parent job.

The dedicated [SerpApi Google News API](https://serpapi.com/google-news-api) receives one canonical venue-name/city query with `when:90d`, English/India localization and `no_cache=true` only for this engine. The application retains its own one-hour shared cache and the original provider ID/retrieval time on reuse. There is no auto-refresh, pagination, story-token follow-up, article fetch or image analysis. Groups/highlights/stories are flattened with32 candidate/12 retained article bounds. URLs, publisher names, supplied headlines/snippets and exact ISO dates are projected; absent snippets or dates are not invented. Unknown provider error shapes stay failures.

Literal topic and venue/area labels support review rather than establish present incidents or branch identity. Recent publication means within14 days of original retrieval; a newer-than-brief badge compares publication to the saved brief snapshot. Questions combine those topics with private selected requirements locally and are never sent. Area news cannot establish venue impact; no matching report is not an all-clear. News never confirms current lift operation or changes the deterministic accessibility verdict. Old checks remain readable after expiry; a fresh check requires explicit user action. All global/day/session/allocation budgets and the protected reserve apply.

## Budgets and retention

The owner-requested balance policy supersedes the original universal five-search cap. A server-side account check is required for a new run, and account data older than 60 seconds is refreshed before an active run dispatches another search. Atomic reservations after that account snapshot reduce its conservative effective remaining estimate. Above 50 remaining credits, a new investigation receives the expanded finite evidence menu. At 50 or fewer, or without a fresh confirmed balance, the five-search policy applies. Crossing the threshold during a run prevents checks beyond five; completed work is retained. Existing saved runs keep their original ceilings and are displayed as legacy runs.

Discovery ≤1 SerpApi attempt. Expanded investigation ≤26 SerpApi and 56 LLM attempts: two baseline requests plus at most one keyword-review, one general branch-snippet and one observed-domain check for each of eight unresolved must-have features. Missing identity/domain or visited action keys remove choices; sufficient evidence stops unnecessary checks. Credit-conserving mode retains the original smaller review/web menu and five searches. Planner consumes a call only while preserving a future extraction call, otherwise uses labeled deterministic fallback. Public snippets and review samples remain bounded; there is no unlimited pagination or arbitrary URL fetching. Provider-billed allowance may differ from conservative application attempts.

New-policy jobs with a configured full search ceiling above five have corpus ceilings of 160 immutable source snapshots, 128,000 text characters, 192 claims and 48,000 combined quote/scope characters. These storage bounds remain in effect if low allowance reduces that job's dispatch ceiling to five; reducing searches does not discard saved evidence. Legacy jobs and owner-configured full ceilings of five or fewer retain 60 / 48,000 / 96 / 24,000. A corpus limit produces an explicit partial brief, never silent evidence loss or invented conclusions.

Default buckets: global from real account allowance minus the 30-credit protected reserve and no more than the 220 owner ceiling, session 64 searches (`SERPAPI_SESSION_ATTEMPT_CAP`), UTC-day 60 searches, and saved job caps. Verification jobs additionally share the unchanged durable 30-search allocation. Reconciliation reduces total caps safely relative to consumed units; increases are separate audited owner actions. Account refresh does not replenish used counters or bypass the verification allocation. Environment and DB kill switches must both permit dispatch. Cache reads remain available when disabled. No automatic monthly reset or detached background worker.

Owner retention defaults: raw cache payloads7 days; normalized evidence/private reports30 days; sessions24 hours. Dry-run/delete scripts preserve provider/reservation audits required for current caps. No cron, vector DB, full HTML/images or arbitrary URL fetching.
